# Opt-in CLAP whole-block delivery

A caller holding `Box<dyn Plugin>` can call ordinary `prepare`, then `prepare_block_delivery(BlockDeliveryCapacity { targets, notes })` on the control owner. This reserves delivery storage fallibly for a registered catalog of at most 4096 parameters, at most 4096 configured targets and at most 1024 explicit notes. Unsupported processors return `BlockDeliveryError::Unsupported` without processing. This does not replace ordinary audio preparation or promise that a third-party allocator or activation callback succeeds.

`process_block_delivery` accepts explicit `BlockTarget` absolute values and ordered `BlockNote` records. Registered IDs are looked up through a control-prepared sorted index. Values use existing declared clamping, including the existing NaN default. Duplicate target IDs use the last supplied value; an empty batch retains configured targets. The entire batch, capacity, channel shape and positive span are admitted before latest targets change or processing begins. Note offsets must be nondecreasing and within the span. Blocks larger than the prepared maximum are refused, never split. A successful call invokes the processor once, returns its valid `BlockProcessStatus`, and reports the frames and actual target/note records attempted. Successful repeated blocks allocate no delivery storage. No receipt is issued for inactive, skipped, failed or invalid-status processing.

A processor failure silences only the supplied span and invalidates target acknowledgements. The next block retries all latest configured absolute targets, including unchanged values; newer values supersede failed ones. Notes belong only to their explicit call and are never automatically replayed after uncertain processing. Admission refusal does not consume the caller's batch. `clear_block_delivery_targets` forgets targets without changing processor state or inventing defaults. Reset retains latest targets and invalidates acknowledgements. Ordinary reprepare invalidates delivery preparation and retains latest targets for the next successful delivery preparation. Successful state load clears latest targets; failed state load retains them and invalidates acknowledgements.

The legacy queue and this API must not be mixed implicitly. Legacy setters, note methods and processing clear prior opt-in targets and acknowledgements and invalidate opt-in preparation without changing legacy behavior. Repreparing delivery after a legacy intervention therefore does not replay earlier opt-in targets. Delivery preparation refuses a pending legacy queue; the caller must drain it through ordinary processing before preparing delivery again. This API takes explicit notes directly and does not populate the legacy held-note tracker. Reset is the explicit processor note-recovery boundary.

The receipt proves a valid whole-block processor return, not that an arbitrary plugin obeyed every event. Owned synthetic processor receipts and PCM test consumption independently. Mix does not consume these receipts; its legacy setter retry/cache work, catalog/default policy, other hosted formats, timing within blocks, installed processors and physical-device deadlines remain separate capabilities.
